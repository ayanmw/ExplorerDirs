# Q-Dir 原生布局编号与窗格对应

2026-10-21 建立六种映射；2026-10-23 补齐镜像三窗格和条带布局后，当前十二种应用布局均有 Q-Dir 基础字段映射。
证据来自本机 Q-Dir 12.79 的只读静态分析及独立代码复核，**尚未在 Q-Dir 可见窗口中读取导出文件**。
不把本程序往返测试称为 Q-Dir GUI 验收。

导入时先按 Q-Dir 原始编号读取每窗格标签、`CurPos`、查看设置，
再将整个窗格及其选中索引一起转换到应用顺序。导出基础字段使用反向排列。
本程序扩展始终存储应用自己的完整快照和固定标签编号，不重复转换。
基础字段被外部修改后，既有哈希检查仍使过期扩展失效。

已映射本机 12.79 的全部 0～11 编号。其他未知编号不近似替换，
导入提示未支持，保持当前布局及原始窗格编号。分隔比例已按[比例兼容](qdr-proportions.md)接入；独立上下纵向分隔线和窗口位置仍未支持。

## 活动窗格 `Focus`

2026-10-21 补齐基础字段 `Focus`。它采用 **0～3** 的原生窗格编号，
与 `Dir1`～`Dir4` 的后缀相差 1。例如上下双窗格的下窗格对应 `Dir3`、`Focus=2`，
导入到应用窗格 2；左大右双的右下窗格对应 `Dir4`、`Focus=3`，导入到应用窗格 3。

导入时按同一映射转换，只恢复已知布局中可见、且至少有一个可导入标签的窗格。
缺失字段或 Q-Dir 的 `-1` 哨兵表示没有指定活动窗格；非法值、未知布局、隐藏窗格
或没有可导入标签的目标会提示并不应用该字段。不会为恢复活动窗格而切换布局，
也不会激活一个仅剩本程序原有标签的窗格。确认对话框显示转换后的活动窗格。

导出写入 `AppToNative[ActivePane]`。`Focus` 纳入基础字段哈希，外部修改后原扩展失效；
旧导出中没有这个字段时，原哈希算法结果不变，仍可通过扩展恢复应用活动窗格。
有效扩展始终优先使用自身应用编号。此处恢复的是应用的活动窗格选择；
实际键盘焦点和 Shell 文件项目焦点仍需 GUI 单独验收。

本机同一二进制的独立读写证据：

- `0x46d02e` 查找 ASCII `Focus`（字符串 `0x52e1fc`），通过 `0x45cad8` 读取整数，
  缺失时使用传入的既有值；`0x46d065` 保留结果，没有加减 1。
- `0x46da6d` 跳过负数；`0x46da72` 将该值传给 `0x456648`，
  后者按 0、1、2、3 分别返回原生窗格 1、2、3、4 的对象地址。
- 保存侧 `0x45d439` 调用 `0x456060`，依次判定四个窗格并返回 1～4，无对应窗格返回 0。
  `0x45d5a8` 减 1，`0x45d5ba` 将结果写入格式参数位置。
  UTF-16 格式串 `0x52d8a0` 的第 16 个 `%d` 为 `Focus`（第 17 个为 `colorthema`），
  对应调用栈的 `+0x88`，因此未指定时写 -1，四个窗格写 0～3。

测试先复现原导出没有 `Focus`，再验证全部六种布局的每个可见窗格；
覆盖原生输入、直接检查输出字段、无扩展恢复、隐藏/空窗格、未知布局、非法值和缺失/-1，
以及修改 Focus 后的扩展失效、旧无 Focus 扩展读取。构建 0 警告/0 错误，Settings smoke 通过。
这些证据不代替 Q-Dir 实际读取导出文件。
独立代码复核确认读写链路、零起始编号及 -1 哨兵、转换方向和旧无 Focus 扩展兼容，
未发现阻断问题。原生读取器对其他负数也跳过恢复，对部分超范围非负数回退首窗格；
本程序对这些非正常保存值明确提示，不复制其宽松回退。

## 独立证据

分析对象为用户提供的 `C:\SoftwareOK\Q-Dir\Q-Dir.exe`：

- 文件版本：12.79（以本地文件版本信息为准）。
- SHA-256：`9ADAA5994A476F06F0DC9CDF5EAE9CC0986CBFC43055FB9F05341F803FB21FCA`。
- PE64 映像基址 `0x400000`，下列为该文件的静态 VA。
- 未执行、注入或修改 Q-Dir，没有复制其二进制、资源图或实现代码进仓库。
  临时反汇编输出仅位于被忽略的 `src/.state/qdr-layout-analysis/`。

| 核查点 | 地址 / 观察结论 |
| --- | --- |
| 布局字段入口 | UTF-16 `ViewMode` 位于 `0x52e208`；`0x46cdf6` 起查找字段并转整数，`0x46d635` 将值加 `0x8497` 后发送 `WM_COMMAND` |
| 布局分支 | `0x46bda4` 起从命令减去 `0x8497`，按原生布局值分支；存储位置在对象 `+0xc0c` |
| 窗格绑定 | `0x469086`～`0x46923e` 将根分隔器绑定到两个子容器；首子分隔器绑定窗格 1、2，次子分隔器绑定窗格 3、4 |
| 编号与配置对应 | `0x46d10d`～`0x46d17d` 对四个窗格分别传入对应编号；`0x4cf69d` / `0x4cf74e` 使用编号及编号加标签索引生成字段后缀 |
| 分隔方向 | `0x43e77c`：方向 1 采用左右调整光标，方向 0 采用上下调整光标；`0x42a184` 的矩形计算独立确认 1 为左右、0 为上下，子项 0 在左/上 |
| 收起侧 | 布局处理器通过隐藏子项 1、将分隔器单侧模式置 0 收起右/下侧；结合分隔方向和绑定关系得出上表 |

例如编号 4 保持根上下分隔，分别收起两个子分隔器的第二侧，
故显示窗格 1、3。编号 9 将根设为左右、右子容器设为上下，
收起左子容器第二侧，故显示左 1、右 3/4。编号 10 的配置相反，
是左双右大，不能用来导出应用的“左大右双”。

[官方 FAQ 117](https://softwareok.de/?faq=117&seite=faq-Q-DIR) 的示意图给出了 0 和 11 两个端点，
但没有足够信息独立证明中间各值。
[官方语言表](https://www.softwareok.com/?seite=Freeware/Q-Dir/language/English-UK)提供布局名称；
本机静态菜单资源的部分文字编号与实际几何分支不一致，因此**不以菜单顺序或静态文字编号推导布局**。

## 验证与限制

### 2026-10-23 条带布局补齐

重新核对目标 SHA-256 与上文一致。既有静态分支 `0x46c04b` 的原生 5 显示四窗格，
`0x46c06a～0x46c0d2` 将根与两子容器全部置为左右方向 1，恢复三个分隔器双侧，
所以从左到右为 1、2、3、4。原生 6 从 `0x46c08f` 分支将同样三处置为上下方向 0，故为四行。
原生 7 从 `0x46c0dc` 显示 1/2/3、隐藏 4，将三处置为左右；
原生 8 从 `0x46c123` 同样显示前三窗格，将三处置为上下。
二者经 `0x46c298` 共用路径收起第二子容器第二侧，形成三列/三行。仅保留字段/几何事实，未复制实现代码。

新增应用 ID 9～12。分隔条逐边界生成，保留全部窗格对象；条带比例单独保存三或四项权重，
均分不依赖旧两轴值。无窗口几何检查覆盖默认等分、逐条分隔线改变和取消、实际占位与隐藏窗格，

## `TreeNsplit` 宽度字段证据（2026-10-28）

Q-Dir 官方 [FAQ 117 示例](https://www.softwareok.com/?faq=117&seite=faq-Q-DIR)给出
`Tree1split`～`Tree4split=2500`，但没有定义这些值的单位或换算方式。本机 Q-Dir 安装目录中
`start.qdr`、`start2.qdr` 和一份收藏样本也全部为 `2500`；项目中发现的 275 份 `.qdr` 文件
大多是 GUI smoke 生成夹具，值也全为 `2500`，不能视作 275 个独立布局样本。

现有证据无法区分 2500 是 25% 比例、归一化整数还是其他编码，也没有不同宽度样本可校准。
因此导入器继续提示未应用 `TreeNsplit`，不把它写入 `NavigationTreeWidths.ini` 或本程序扩展；
需要一份通过 Q-Dir 实际调整树宽度后保存的 `.qdr`，再配合可见宽度对照，才能确认换算。
